### **Instructions**

This project is about creating a gym analytics solution. The pipeline looks as follows: - webhook-dispatcher - for receiving all data - {source_name}-enricher - in case the data needs to be enriched it happens here, source specific. - {source_name}-translator - translate the data into one generic event format. - {output_name}-listener - listen to selected events, if necessary translate them in the requested format and send them. The project is now a minimum viable product, but needs to be sold as a saas product with multiple tenants. See it as a managed HubSpot for Gyms. For this project there are some architectual choices made: - scalability first; - keep it simple; re-use of services - write in python - write and deploy using the same packages When writing or editing code, please share complete code that can be copy-pasted for deployment. Also, when sharing code, add the deployment command for the terminal. Include the folder selection (e.g. cd ~/Documents/Code/sportivity-enricher). The project is hosted in Google Cloud with id: solid-future-452906-a2. Region: europe-west1. It is no option to deploy gen1 services. Use the latest python version. As said, architecture is important. In case of planning designing new features or debugging of issues, we start conversating about the problem and solutions. Please in that phase do not write code, but wait for the command to do so. Especially in debugging, please only share the task that you want input for and not a list that contains too many steps. Fields need to be named snake case. Never remove code from files without first sharing what the code does and asking if it can be removed. Event Naming format: channel_action Format. When creating a service, please log the input and output json, so I can quickly verify what the service did. When creating events for topic 'events', usually done by the {source}-translator, please use format ISO 8601 strings. We use gen2 functions, mostly using pub/sub. In the code use Gen 2 CloudEvent signature and stick to it. Do you see a good reason, knowing our principles, please first discuss. When webhooks come in, the events will mostly be posted to {source}-enrichments. But sometimes it is not needed to enrich and the event will then be posted directly to {source}-translations. The {source}-enricher functions will publish to topic {source}-translations. The {source}-translator functions will post to the generic topic 'events'. {source}-listener functions listen to the topic events for input. Enrichment services have the goal of enrich events with additional data. Translation services have the goal of transforming data of the events into a generic format. Listener services have the goal to send data to a receiving party. It often also needs to translate fields. In case an error occurs in a service, this should be added to the LOG of the service. But also an event should be published to topic 'events', with email dennis@habits.fit. In The payload the service name should be mentioned and very bold the error description.
