### **Instructions**

This project is about creating a gym analytics solution. The pipeline looks as follows: - webhook-dispatcher - for receiving all data - {source_name}-enricher - in case the data needs to be enriched it happens here, source specific. - {source_name}-translator - translate the data into one generic event format. - {output_name}-listener - listen to selected events, if necessary translate them in the requested format and send them. The project is now a minimum viable product, but needs to be sold as a saas product with multiple tenants. See it as a managed HubSpot for Gyms. For this project there are some architectual choices made: - scalability first; - keep it simple; re-use of services - write in python - write and deploy using the same packages When writing or editing code, please share complete code that can be copy-pasted for deployment. Also, when sharing code, add the deployment command for the terminal. Include the folder selection (e.g. cd ~/Documents/Code/sportivity-enricher). The project is hosted in Google Cloud with id: solid-future-452906-a2. Region: europe-west1. It is no option to deploy gen1 services. Use the latest python version. As said, architecture is important. In case of planning designing new features or debugging of issues, we start conversating about the problem and solutions. Please in that phase do not write code, but wait for the command to do so. Especially in debugging, please only share the task that you want input for and not a list that contains too many steps. Fields need to be named snake case. Never remove code from files without first sharing what the code does and asking if it can be removed. Event Naming format: channel_action Format. When creating a service, please log the input and output json, so I can quickly verify what the service did. In the code use Gen 2 CloudEvent signature and stick to it. Do you see a good reason, knowing our principles, please first discuss. When webhooks come in, the events will mostly be posted to {source}-enrichments. But sometimes it is not needed to enrich and the event will then be posted directly to {source}-translations. The {source}-enricher functions will publish to topic {source}-translations. The {source}-translator functions will post to the generic topic 'events'. {source}-listener functions listen to the topic events for input. Enrichment services have the goal of enrich events with additional data. Translation services have the goal of transforming data of the events into a generic format. Listener services have the goal to send data to a receiving party. It often also needs to translate fields. In case an error occurs in a service, this should be added to the LOG of the service. ## **[BUSINESS.md](http://BUSINESS.md)**

`# Habits — Business`

 ``

`## Missie`

 ``

`Sportscholen helpen succesvol te zijn — en daarmee zo veel mogelijk mensen gezond houden.`

 ``

`---`

 ``

`## Propositie`

 ``

`Habits perst meer winst uit een sportschool.`

 ``

`Het kernprobleem: gymoperators ontwerpen processen eenmalig en focussen daarna op de kwaliteit van uitvoering. Ze draaien hetzelfde draaiboek jaar na jaar, omdat ze geen data hebben die laat zien wát werkt en wát niet. Ze optimaliseren de uitvoering van suboptimale processen.`

 ``

`Het gevolg: 20–30% preventable churn die niet zichtbaar is als probleem, omdat het altijd al zo was.`

 ``

`De analogie die alles verklaart: geen topsporter verbetert door altijd op dezelfde manier te trainen. Je meet, past aan, herhaalt. Gyms coachen dit dagelijks aan hun leden — maar passen het nooit toe op hun eigen bedrijfsvoering.`

 ``

`**Habits is progressive overload voor gym-retentie.**`

 ``

`Het systeem start een continue verbeteringscyclus: processen worden niet eenmalig ontworpen maar continu verbeterd op basis van data en AI. Wat het oplevert groeit mee — niet statisch, maar compounding.`

 ``

`---`

 ``

`## Doelgroep`

 ``

`**Koper: de franchisenemer of eigenaar**`

`Denkt in marge, retentie en schaalbaarheid. Wil zien of de investering rendeert. Heeft geen behoefte aan een dashboard — wil resultaat.`

 ``

`**Dagelijkse gebruiker: de locatiemanager**`

`Verantwoordelijk voor team en leden. Heeft weinig tijd. Werkt vanuit Slack. Heeft behoefte aan concrete actie, niet aan interpretatie.`

 ``

`**Uitvoerder: de medewerker**`

`Voert taken uit op de vloer. Heeft baat bij duidelijke instructie en directe feedback.`

 ``

`---`

 ``

`## Wat Habits doet`

 ``

`Habits combineert twee pijlers die elkaar versterken:`

 ``

`### 1. Ledenretentie`

`De Habit Health Index (HHI) maakt per lid en per locatie inzichtelijk waar retentierisico zit — over drie journeys (Onboarding, Member Maintenance, Reactivation) en drie dimensies (Retentiescore, Customer Success Score, Progressiescore).`

 ``

`AI-coaching via Slack begeleidt managers bij het interpreteren van deze data en het verbeteren van de onderliggende processen. Niet eenmalig, maar wekelijks. Het systeem leert welke interventies werken en past zijn aanbevelingen aan.`

 ``

`### 2. Teamprestaties`

`Operationele taakuitvoering wordt inzichtelijk gemaakt via dagelijkse en wekelijkse rapporten. FitCheck-feedback van leden koppelt terug naar medewerkersniveau. Dit maakt coaching concreet en meetbaar.`

 ``

`Team en resources zijn secundair — ze dienen ledenretentie.`

 ``

`---`

 ``

`## Definitie van succes`

 ``

`| Uitkomst | Meetpunt |`

`|---|---|`

`| Hogere ledenretentie | Retentie na 30 / 90 / 180 dagen |`

`| Hogere leadconversie | Ratio proefweek → lidmaatschap |`

`| Snellere opvolging | Responsetijd op leads en taken |`

`| Betere teamadoptie | % taken uitgevoerd binnen tijdvenster |`

`| Heractivatie | Ratio terugkerende leden na uitval |`

 ``

`Succes is niet het gebruik van het systeem — het is aantoonbare verbetering van deze uitkomsten over tijd.`

 ``

`---`

 ``

`## Businessmodel`

 ``

`SaaS voor gymoperators, aangeboden per locatie. Multi-tenant: elke locatie of keten is een aparte tenant met eigen data, eigen configuratie en eigen doelen.`

 ``

`Primaire testomgeving: Basecamp Fitness.`

 ``

`---`

 ``

`## Beslissingen`

 ``

`**Continuous improvement, geen early-warning tool**`

`Habits is geen systeem dat brand blust. Het start een continue verbeteringscyclus waarbij processen structureel beter worden op basis van data. De waarde groeit compounding — niet lineair.`

 ``

`*Waarom*: vroege positionering als early-warning tool bleek te smal. Het echte probleem is dat gymoperators processen eenmalig ontwerpen en daarna nooit verbeteren, omdat ze geen data hebben die laat zien wat werkt.`

 ``

`**De koper is de eigenaar of franchisenemer**`

`Habits wordt verkocht aan de eigenaar, niet aan de manager. De eigenaar denkt in marge, retentie en schaalbaarheid en beoordeelt Habits op aantoonbaar resultaat.`

 ``

`*Waarom*: de manager is de dagelijkse gebruiker maar heeft geen beslissingsbevoegdheid over tooling. De eigenaar heeft de pijn én het budget.`

 ``

`**Ledenretentie is de primaire waardedrijver**`

`Alles wat Habits doet, dient uiteindelijk ledenretentie. Teamprestaties, rapportages en coaching zijn middelen — geen doel op zich.`

 ``

`*Waarom*: retentie is direct meetbaar in omzet en marge. Het is de metriek waarop eigenaren worden afgerekend en waarop Habits zijn waarde moet bewijzen.`

 ``

`**HHI als centraal meetsysteem**`

`De Habit Health Index is het primaire instrument om retentiegezondheid per lid en per locatie inzichtelijk te maken. Alle coaching en rapportage is hierop gebaseerd.`

 ``

`*Waarom*: een gedeeld meetsysteem maakt vergelijking tussen locaties en over tijd mogelijk. Zonder gemeenschappelijke meetlat is continuous improvement niet schaalbaar.`

 ``

`**Rapportagelaag voor de eigenaar is een open ontwerpkeuze**`

`De eigenaar heeft mogelijk een andere rapportagelaag nodig dan de manager. Dit is nog niet uitgewerkt en wordt bepaald op basis van wat we leren in de praktijk.`

 ``

`*Waarom*: te vroeg specificeren leidt tot bouwen voor een aanname. Basecamp Fitness als testomgeving levert de input om dit te beslissen.`

 ``

`**Conversational UX als richting**`

`De primaire interactie verloopt via gesprekken — nu via Slack. Managers en medewerkers hoeven geen nieuw systeem te leren. Hoe dit er voor de eigenaar uitziet is een open ontwerpkeuze.`

 ``

`*Waarom*: adoptie is de grootste risicofactor bij het introduceren van nieuwe tooling in een gym-omgeving. Een interface die zich gedraagt als een gesprek verlaagt de adoptiedrempel maximaal.`

 ``

`**Multi-tenancy als first-class concern**`

`Elke tenant — locatie of keten — heeft volledig geïsoleerde data, configuratie en doelen. Er is geen gedeelde state tussen tenants. Nieuwe tenants voegen data toe zonder architectuurwijziging.`

 ``

`*Waarom*: Habits is een SaaS-product. Compromissen in tenant-isolatie zijn later vrijwel onmogelijk te repareren zonder data-migraties en downtime. Dit moet van het begin af aan kloppen.`

 ``

`**All-in op AI**`

`Habits wordt gebouwd als een AI-first systeem. Dat betekent dat het systeem leert van gedrag, zichzelf verbetert via feedbackloops, en over tijd minder menselijke sturing nodig heeft — niet meer. Handmatige configuratie is een tijdelijke oplossing, nooit een eindtoestand.`

 ``

`*Waarom*: de waardepropositie van Habits is continuous improvement. Dat is alleen schaalbaar als het systeem zelf verbetert — niet als elke verbetering handmatig wordt doorgevoerd. Een systeem dat afhankelijk blijft van menselijke configuratie schaalt niet naar meerdere tenants.`

 ``

`**Kennis en uitvoering zijn gescheiden**`

`Domeinkennis over wat werkt — welke interventie past bij welk ledenprofiel, welke timing effectief is — staat los van de code die het uitvoert. Kennis leeft in data en documenten. Code implementeert.`

 ``

`*Waarom*: als kennis in code zit, vereist elke verbetering een deployment. Als kennis in data zit, kan het systeem leren en aanpassen zonder codewijziging. Dit is de voorwaarde voor een zelflerend systeem.`
